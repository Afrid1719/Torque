## Request and Response Flow

A request moves through the following layers:

User
→ React Frontend
→ API Client
→ FastAPI Router
→ Authentication and RBAC
→ Pydantic Validation
→ Service Layer
→ Repository Layer
→ SQLAlchemy Session
→ MySQL

The response returns through the repository and service layers, is serialized through a Pydantic response schema, and is returned to the frontend as JSON.

Errors from authentication, validation, business rules, or database operations are handled centrally and converted into controlled API responses.

## Database Migration Strategy

TORQUE uses Alembic as the exclusive mechanism for database schema changes.

SQLAlchemy models define the desired database structure, while Alembic migration files define how the database moves between schema versions.

The application will not use `Base.metadata.create_all()` during normal startup.

Migration policy:

- Schema changes must be introduced through Alembic revisions.
- SQLAlchemy model changes and their migration files must be committed together.
- Autogenerated migrations must be reviewed manually.
- Migration upgrades must be tested before merging.
- Migration downgrades should be tested where practical.
- Applied migrations must not be edited after they reach a shared environment.
- Corrective changes must be introduced through a new migration.
- Seed or demonstration data must be handled separately from schema migrations.
- Destructive changes require additional review and backup consideration.
- Migrations are applied explicitly before application startup or deployment.
- FastAPI workers must not execute migrations automatically.

Expected workflow:

1. Modify SQLAlchemy models.
2. Generate an Alembic revision.
3. Review the generated upgrade and downgrade operations.
4. Apply the migration locally.
5. Verify the resulting schema.
6. Test the downgrade where practical.
7. Apply the migration again.
8. Commit the model and migration in the same pull request.

## Machine Learning Model Loading Strategy

TORQUE loads the predictive-maintenance model once during the FastAPI lifespan startup.

The persisted artifact should contain the complete inference pipeline, including preprocessing, feature ordering, and the trained Random Forest classifier.

The model must not be loaded inside individual prediction requests.

Model lifecycle:

1. FastAPI starts.
2. Application configuration is loaded.
3. The model artifact and metadata are located.
4. The artifact is loaded from a trusted application-controlled location.
5. Model version and expected features are validated.
6. A basic inference smoke test is performed.
7. The loaded model is stored in an application-level model registry.
8. Prediction services reuse the loaded model.

The model registry should maintain:

- Loaded pipeline reference
- Model version
- Expected feature names
- Model availability status
- Loading timestamp

Failure policy:

- Core workshop functionality must remain available if the ML model fails to load.
- Only predictive-maintenance endpoints should become unavailable.
- Prediction endpoints should return HTTP 503 with a controlled error response.
- Internal file paths, stack traces, and serialization details must not be exposed.
- ML availability should be reported separately from general application health.

Model replacement policy:

- Hot reloading is outside the MVP scope.
- A new model must be versioned and exported as a trusted artifact.
- The application must be restarted to load the new model.
- Each FastAPI worker loads its own in-memory model instance.

Security requirements:

- Only trusted model artifacts may be loaded.
- Model files must not be accepted through public upload endpoints.
- Training and production dependency versions should be recorded.
- Model metadata should include feature names, model version, training timestamp, and evaluation information.

## Frontend UI Framework Decision

TORQUE uses Material UI as the frontend component library.

Material UI was selected because the application requires form-heavy screens, dashboards, tables, dialogs, status indicators, and role-specific layouts. Using a mature component library reduces custom UI implementation effort and helps maintain visual consistency across the application.

TailwindCSS is not used in the MVP frontend.
